# Iteration 027: recover from WebGPU device loss

Scope: [Brief 2.2](../briefs/BRIEF-2.2-device-lost.md), following the published [v0.3.0 review](../reviews/v0.3.0.md).

## Cause and baseline

The unmodified built app reproduces the eval failure in auto mode; forced WebGL2 passes. Preserve the [baseline report](027-baseline-eval.json) and its [WebGL2 screenshot](027-baseline-webgl2-seed-1.png).

A separate bare page on the same secure origin creates a WebGPU adapter/device and submits only a clear pass. It loads no island/Three.js modules, retains the adapter and device, and instruments `GPUDevice.destroy()`. The device is nevertheless lost with reason `destroyed`, message `Device was destroyed`, and `OperationError: A valid external Instance reference no longer exists`. The trace records no JavaScript `destroy()` call. Before this fix, the island reproduced the same loss without a `destroy()` call: [probe evidence](027-device-probe.json).

Reproduce after building with `node scripts/probe-device.mjs --step NNN` (choose an unused step). The script uses the eval browser flags and refuses to overwrite earlier evidence.

This isolates the immediate loss to the headless Chromium WebGPU environment, rather than island disposal or a shared scene device. It does not identify a specific upstream driver defect or establish that physical GPUs behave the same way. No browser flags, eval thresholds or dependencies were changed to make the eval pass.

## Changes

- Install `renderer.onDeviceLost` before initialization, including on each separate fallback attempt. A device watch rejects pending initialization/compilation/fence work and refuses subsequent draws, resizes or quality changes from that renderer.
- Handle recoverable loss without sending Three.js's default fatal console error: the app owns the stop/rebuild path and shows a switching/restored notice. Genuine failure of WebGL2 remains an error with retry guidance.
- Rebuild on a fresh forced-WebGL2 renderer and canvas from the same captured `WorldData`. Generation happens once outside the recovery controller; there is no page reload or new seed. Startup loss and loss after publication share the same one-way fallback path.
- Give each frame loop a generation token and cancellable resize/visibility listeners. Stop the loop, hide/reset the backend/FPS labels and cover the canvas before rebuilding. Pending callbacks and repeated/late loss reports cannot publish an old renderer into the current HUD or start competing fallbacks. Publish the backend label only after a successful draw/fence.
- Retire old device listeners and release owned geometry, materials, post-processing/shadow targets and the ocean height texture. A pending renderer initialization is allowed to settle before its renderer cleanup runs; abandoned work cannot take over the fresh canvas.
- Preserve loading stages, GPU warm-up, adaptive quality, manual entry for slow software devices and first-600-frame diagnostics.

## Validation

Build passes with the existing bundle-size advisory. All 47 tests pass, including 10 new device/recovery tests: pending init/fence interruption, retired/late callbacks, startup fallback with the same world reference, live loss, synchronous loss during publication, duplicate frame/loss reports, fallback failure and explicit WebGL2 failure.

`npm run eval` passes **30/30** with its unchanged default settings: auto and forced WebGL2, seeds 1 / 7 / 42 / 99 / 2026, three runs per seed/mode. Auto loads encounter the actual native device loss and recover to WebGL2; explicit WebGL2 loads also pass. No page errors are reported. Every load passes the existing blue/land/black/flat pixel checks. Software rendering uses the existing explicit Enter path; timing is reported, as the original harness specifies.

Retain the [full JSON](027-eval.json), [summary table](027-eval-summary.md) and all 30 eval screenshots, with mode/run suffixes before the seed in their tracked names. The owner harness and its thresholds are unchanged.

The [focused browser check](027-focused-device.json) also passes: one native device-loss event, one page navigation, one world-generation start, one canvas, and a working WebGL2 scene for seed 42 with its 331 trees. The restored notice is present. Deliberately losing the replacement WebGL2 context then produces the expected error state, `graphics unavailable` label and `renderer unavailable` counter. Its one fatal console error is intentional and separate from the clean 30-load eval.

Reproduce with `node scripts/check-device-recovery.mjs --step NNN` after building, using an unused step. This check intentionally ends by destroying only its headless page's WebGL2 context. Software timings do not establish physical GPU performance. Native WebGPU devices that remain healthy are unavailable in this environment, so live WebGPU loss is exercised through the recovery-controller tests; actual native startup loss is exercised by every auto-mode eval load.

## Screenshot findings

Inspected all 33 PNGs: the baseline, all 30 eval loads (every seed/mode/run) and both focused device-check captures. Every normal eval image shows a complete island, blue water/sky, shoreline foam and a readable **WebGL2** label with the low-quality/FPS HUD. No auto-mode frame remains blank, black or stuck on the startup error. The soft edges in low quality are the existing resolution fallback, not a new fidelity claim.

- Auto recovery: all 15 captures include the short **Graphics restored · WebGL2** notice below the island. It is readable and does not cover terrain or the top HUD. The focused [notice capture](027-recovered-notice-seed-42.png) shows the same behaviour with a complete seed-42 island.
- Same world: matching auto/forced-WebGL2 seeds retain identical land silhouettes, tree groves and framing, allowing for animated water/foam phase. Seed 1 retains its two mountainous ends, seed 7 its bay, seed 42 its foreground peak, seed 99 its offshore islet, and seed 2026 its larger mountain. The focused browser assertions establish one generation and one navigation; static images alone do not prove those lifecycle facts.
- Forced WebGL2: all 15 normal captures have complete scenes and backend labels without a spurious recovery notice. Seed-1 output also matches the preserved baseline appearance.
- Stopped renderer: after intentionally losing the fallback context, the [failure capture](027-webgl2-lost-seed-42.png) covers the island with a clear context-loss/retry screen. The focused DOM assertions verify **graphics unavailable** and **renderer unavailable** rather than a stale renderer/FPS claim.
- The immediately sampled FPS in the focused notice image is still settling; none of these short software captures establishes hardware FPS. Live WebGPU loss after a healthy native session is covered by the controller tests, not represented as a hardware screenshot result here.
