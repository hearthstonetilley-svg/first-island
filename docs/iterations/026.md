# Iteration 026: staged loading screen and gated fade-in

Scope: the owner's loading-screen addition to [Brief 2.1](../briefs/BRIEF-2.1-first-load-fps.md). This continues the same performance job after [025](025.md).

## Changes

- Add a full-screen ocean-coloured loading view with a progress bar, current task, milestone markers and seed. Include small-screen layout, accessible progress/status labels, keyboard-focusable actions and reduced-motion support.
- Generate terrain and place trees in awaited chunks so the browser can paint actual progress. Both the synchronous world API and the browser path consume one generator and preserve the seeded PRNG order. Progress advances at completed rows, placement batches and rendering stages; the percentages weight stages, rather than claim to measure elapsed time or count every driver pipeline.
- Report generation, tree placement/canopy construction, renderer initialization, water compilation, terrain/lighting compilation, post-processing and GPU warm-up. Compile water explicitly against the same target/MRT as the scene; hidden full-graph renders still cover internal post/shadow pipelines and both quality variants.
- Keep the loading screen up after precompilation while checking two-second frame windows. Automatic entry requires median ≤25 ms and 95th percentile ≤50 ms. Quality steps run behind the screen first (pixel ratio, then AO), with fresh readiness windows after a change. Hidden tabs and resizing reset the check.
- Fence GPU completion between covered probe frames. The first probe exposed an important false positive: a covered canvas can deliver fast RAF callbacks while expensive GPU work remains queued. Retain that raw [failed gate probe](026-gate-probe-seed-1.json) as part of the iteration record. The corrected gate includes completed rendering before scheduling the next probe; a stalled probe fence is bounded to 10 seconds with an error/retry screen.
- After a passing window, complete the bar and crossfade the loader, canvas and HUD over 850 ms. Reduced-motion users get an immediate transition. Visible water/tree animation starts at entry. The permanent first-600-frame recorder starts at entry too; loading stages, gate windows and automatic/manual entry are recorded separately in `window.__ISLAND_DEBUG__.loading`.
- A device that remains slow at minimum quality gets a clear low-frame-rate notice and an explicit **Enter island** action. It stays covered until a passing window or that action; there is no timeout that silently declares a slow renderer smooth. A renderer failure shows **Try again** and the reason.

## Verification

- Build passes with the existing bundle-size advisory; all 37 tests pass.
- New tests reject a steady slow cadence and frequent hitches, require a full two-second readiness window, and discard pre-change/background samples. Existing bounded compile/fence, fallback and diagnostic tests still pass.
- Async world tests compare full-world SHA-256 fingerprints measured before the refactor for seeds 1, 42 and 2026, including exact terrain and trees. All match, and both generation APIs produce identical data.
- Capture loading states, a 390×844 layout, disabled-graphics failure, a mid-transition frame and final islands for seeds 1, 42 and 2026 plus forced WebGL2. All use the installed software Chromium; no dependencies were installed.
- These software devices cannot meet the smoothness threshold. Final island captures use `--enter-slow` to exercise the actual explicit button; reports mark `entry: manual` and `manuallyEntered: true`. The limited-state capture retains zero visible-frame samples and no entry, demonstrating that the gate keeps the scene covered. Automatic-ready criteria are unit-tested; native GPU automatic entry still needs owner hardware verification.
- For a reproducible mid-fade image, the capture helper pauses only the canvas/overlay CSS transitions at 425 ms, captures them and resumes. [Metadata](026-fade-capture-seed-1.json) records the pause and observed opacity. This is a staged UI snapshot, not a timing/FPS benchmark.

## Reproduce

```sh
node scripts/profile-load.mjs --step NNN --case loading-post --capture-stage post
node scripts/profile-load.mjs --step NNN --case loading-limited --capture-stage limited
node scripts/profile-load.mjs --step NNN --case loading-error --capture-stage error --disable-graphics
node scripts/profile-load.mjs --step NNN --enter-slow --capture-fade --frames 20
```

Use unique step/case names; inspect the screenshots and commit immediately under AGENTS.md. The helper preserves normal app behaviour and marks the manual-entry/fade test actions in its capture record. These short runs verify the loading UI and correct scene output, not hardware FPS.
