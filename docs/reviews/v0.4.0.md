# Review of round 11 (iteration 029, stage 3a): the simulation clock

Published on its own, before bodies, so the foundation is proven in isolation (advisor, stage 2 plan).

What it is: a fixed-tick simulation (one tick = one simulated second) running in a Web Worker, owning its clock,
dials and an append-only event log; time controls (pause, 1x, 10x, 100x); replay that re-applies every logged
intervention at its original tick and verifies the whole event log.

Independent checks by the reviewer on a frozen copy of b37b2a9:
- 53 tests pass.
- Cross-process determinism (not covered by the iteration's own tests): seed 7, 102,777 ticks with dial and speed
  interventions, run in two separate Node processes: identical record hash (048d5bf310a1c6b8) both times, and replay
  from the record reproduces the same hash. (A different seed differs only by its seed field at this stage, since the
  clock has no seed-dependent behaviour yet; that comparison means something once bodies exist.)
- No wall-clock inside the simulation: `Math.random`, `Date.now`, `performance.now` and timers appear only in the
  worker's scheduler, which converts elapsed time into a whole number of ticks and calls `step(n)`. Scheduler drift
  can only change which tick an intervention lands on, and that tick is recorded.
- The build eval was not run locally on this copy; CI gates it on this pull request.

Notes, not blocking:
1. Speed changes are logged as interventions. They do not change state, so this is harmless, but replay-relevant
   and cosmetic interventions should be distinguishable later.
2. The generation counter here is a clock (30 simulated minutes per generation), not biological generations. This is
   not cosmetic: the 3d viability eval must count biological generations (a third-generation birth, a child of a
   child of a founder, with population above zero), never this clock. Pinned with the builder.
3. Separate-process determinism and true replay must become automated evals in 3d (queued to the builder).
